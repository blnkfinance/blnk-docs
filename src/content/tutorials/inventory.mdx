Inventory is how many units of a product you have, and where each one is: in stock, sold, on the way to a buyer, or delivered. Each of those stages is a balance, and moving units from one stage to the next is a transaction, so every count has a history you can replay.

This tutorial shows how to implement that with Blnk.

<TutorialSteps>
  <TutorialStep title="Design the money movement">
    Before we start building, we need to define our [money movement](/ledgers/money-movement-map). This helps us outline how Alice's phones move from her stock to Bob.

    Alice sells the iPhone 16 Black 128GB. She gets 30 phones from her supplier. We move them into her available balance from `@StockIntake`, an [internal balance](/balances/internal-balances) for stock that comes from outside.

    Bob orders 2 phones. They move from available to sold, then to in transit, then to delivered.

    We hold the sale as [inflight](/transactions/inflight/create-inflight) when Bob checks out, so no one else can buy his 2 phones, and commit it when he pays. We record the pickup and the delivery when each one happens.

  <TutorialStep title="Create the ledgers">
    Before we start recording transactions, we need to set up our [ledgers](/ledgers/introduction) to track Alice's stock. We create one ledger for each stage: available, sold, in transit, and delivered.

    Each ledger holds that stage for every product Alice sells. Listing the balances in the available ledger then shows how many of each product she can still sell.

    Create the four ledgers:

<CodeGroup>

  <TutorialStep title="Create an identity">
    An [identity](/identities/introduction) is how we record the iPhone. We'll link its four balances to it, one per stage, so we can see where every unit is.

    Blnk has two identity types, individual and organization. We use organization for the phone and pass its name and category.

    One identity is one seller's stock of one SKU. If another seller lists the same phone, they get their own identity.

    Anything else we want to keep goes in [metadata](/search/metadata). We'll store the phone's SKU (stock keeping unit) there as `sku`, so we can find every transaction for this phone later. We'll also store `item_code` for the iPhone 16 family and `seller_id` for Alice.

    Create the identity:

<TutorialCode>
<CodeGroup>

```bash cURL wrap
curl -X POST "{{CORE_URL}}/identities" \
  -H "X-blnk-key: {{CORE_SECRET_KEY}}" \
  -H "Content-Type: application/json" \
  -d '{
    "identity_type": "organization",
    "organization_name": "{{organization_name}}",
    "category": "{{category}}",
    "meta_data": {
      "seller_id": "{{seller_id}}",
      "item_code": "{{item_code}}",
      "sku": "{{sku}}"
    }
  }'
```

  <TutorialStep title="Receive the stock">
    Alice's 30 phones arrive from her supplier. We move them from `@StockIntake` to her available balance, with the SKU in metadata so this transaction shows up when we read the phone's history in step 10.

    A phone can't be split into fractions, so we set `precision` to `1`. The amount is then just the number of phones, 30.

    `skip_queue` records the transaction straight away, so the 30 phones are ready to sell before Bob orders.

    After the transaction, `@StockIntake` shows -30, one for each phone Alice received.

    <Note>
      For this transaction to go through, we need to turn on [overdraft](/transactions/overdrafts). Without it, `@StockIntake` is created with a 0 balance, and Blnk would reject the record because the source has insufficient units.
    </Note>

    Receive the stock:

<TutorialCode>
<CodeGroup>

```bash cURL wrap
curl -X POST "{{CORE_URL}}/transactions" \
  -H "X-blnk-key: {{CORE_SECRET_KEY}}" \
  -H "Content-Type: application/json" \
  -d '{
    "precise_amount": {{quantity_precise}},
    "precision": 1,
    "reference": "RCV-20261019-090000",
    "description": "Stock received",
    "currency": "UNIT",
    "source": "@StockIntake",
    "destination": "{{destination}}",
    "allow_overdraft": true,
    "skip_queue": true,
```

  <TutorialStep title="Hold the sale">
    Bob checks out with 2 phones. We record the sale from Alice's available balance to her sold balance as [inflight](/transactions/inflight/create-inflight), so his 2 phones are reserved and no one else can buy them.

    Each transaction's reference starts with Bob's order ID, `ord_4412`, and the SKU goes in metadata. `skip_queue` records the hold straight away, so we can commit it in the next step.

    <Tip>
      If Bob's payment fails or he cancels, [void](/transactions/inflight/void-inflight) the hold, and the 2 phones go back to Alice's available balance. Set `inflight_expiry_date` as well, so an abandoned checkout releases the phones on its own.
    </Tip>

    Hold the sale:

  <TutorialStep title="Read the phone's history">
    Every transaction for the phone has its SKU in metadata, so one [filter](/search/db/filtering) on `meta_data.sku` returns its whole history. We sort it by `created_at`, newest first.

    The results show the 30 phones Alice received, the sale hold with its commit, the pickup, and the delivery. If Alice asks why her count changed, this is the record you show her.

    The filter returns 20 results by default. Pass `limit` (up to 100) and `offset` to page through a longer history.

    <Tip>
      With more than one seller, the same SKU can belong to several identities. Add `seller_id` to each transaction's metadata and filter on both fields.
    </Tip>

    Read the history:

<TutorialCode>
<CodeGroup>

```bash cURL wrap
curl -X POST "{{CORE_URL}}/transactions/filter" \
  -H "X-blnk-key: {{CORE_SECRET_KEY}}" \
  -H "Content-Type: application/json" \
  -d '{
    "filters": [
      {
        "field": "meta_data.sku",
        "operator": "eq",
        "value": "{{history_sku}}"
      }
    ],
    "sort_by": "created_at",
    "sort_order": "desc"
  }'
```

```typescript TypeScript wrap
const response = await blnk.Search.filter(

    ],
    sort_by: 'created_at',
    sort_order: 'desc',
  },
  'transactions',
);
```

