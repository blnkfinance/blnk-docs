This guide covers the changes you need to review when upgrading to Blnk v0.15.9.

Before upgrading, check whether your integration assumes every `POST_TRANSACTION` hook signals success, expects `201` for queued duplicates or unknown balances, or matches bulk failure text. Verify that your global webhook handler can receive duplicate deliveries safely. Update those handlers before switching versions. If you store historical balances, plan to refresh the results after upgrading.

## At a glance

| Change | Who is affected? | What changed |
| :-- | :-- | :-- |
| Database migrations | Everyone | Two migrations run with `blnk migrate up`. |
| Hooks for rejected transactions | Apps with `POST_TRANSACTION` hooks | Hooks now also run when a transaction is rejected. |
| Queued create errors | Apps that create queued transactions | A used reference or unknown balance now returns an error instead of `201`. |
| Atomic bulk rollback | Apps that send atomic bulk requests | Queued atomic batches now roll back when a worker rejects an item. Handle the new batch failure event idempotently. |
| Monitor updates | Apps that update balance monitors | A PUT changes only the fields you send. |
| Negative split distributions | Apps that send split transactions | A negative distribution is rejected. |
| Balance history | Apps that read historical balances | Backdated transactions are now counted correctly. |

## Database migrations

0.15.9 adds a column that balance history uses, and drops four database triggers that Blnk no longer uses.

**What to do:** Use a maintenance window. Pause transaction submissions, let existing jobs finish, and stop the old API and workers. Back up the database, run `blnk migrate up`, then start the 0.15.9 API and workers together. If a migration hits its lock timeout, wait for the blocking queries to finish before retrying.

For this upgrade procedure, run the API and workers on the same version. Older workers can apply different queued rollback rules, so keep them stopped once you start 0.15.9.

The trigger migration’s down SQL recreates the four triggers and their function. It cannot replay notifications missed while the triggers were absent. The snapshot migration’s down SQL drops the new sequence column and its stored values. Plan any schema rollback with a database operator and test it on a copy of your database.

## Hooks for rejected transactions

From 0.15.9, a rejected transaction calls your `POST_TRANSACTION` hooks. `data.status` is `REJECTED`, and `data.meta_data.blnk_rejection_reason` says why.

```json Rejected transaction hook (shortened) {5,7} wrap
{
  "transaction_id": "txn_aa13b549-c278-47ee-87d7-2e2cfcad99ce",
  "hook_type": "POST_TRANSACTION",
  "data": {
    "status": "REJECTED",
    "meta_data": {
      "blnk_rejection_reason": "failed to apply transaction to balances: insufficient funds in source balance"
    }
  }
}
```

**What to do:** Check `data.status` before your hook acts on the call. See [Transaction hooks](/webhooks/transaction-hooks).

## Queued create errors

Blnk saves an accepted queued transaction before it answers. A used reference returns `409 TXN_DUPLICATE_REFERENCE`, and an unknown balance returns `404 BAL_NOT_FOUND`. For a single transfer, either error leaves the new attempt without a transaction or `REJECTED` record. A `409` leaves the existing transaction under that reference available for lookup.

With `run_async: false`, queued bulk requests return the error for the failing item and stop adding items there. Items already queued can still process. A split can also have earlier legs saved before a later leg fails.

**What to do:** For a single transfer, look up the original reference on `409`. On `404`, correct the balance ID before retrying. For a bulk request, reconcile by batch ID and reference before retrying any item. Check the individual legs of a failed split. See [Reconcile a queued batch after a duplicate reference](/transactions/bulk-transactions#reconcile-a-queued-batch-after-a-duplicate-reference).

## Atomic bulk rollback

From 0.15.9, when a worker rejects an item in a queued `atomic: true` batch, Blnk refunds applied items or voids inflight items and emits one `bulk_transaction.failed` event for the batch. Blnk records the items still waiting in the queue as `REJECTED` when it reaches them. Before, only `skip_queue: true` rolled back.

If Blnk finds a duplicate reference while adding items to the queue, items already queued may still process, even in an atomic batch. Reconcile by batch ID and reference before resubmitting any items. See [Reconcile a queued batch after a duplicate reference](/transactions/bulk-transactions#reconcile-a-queued-batch-after-a-duplicate-reference).

The failure message now says how many items were refunded, instead of `All transactions in this batch have been refunded`.

**What to do:** Handle `bulk_transaction.failed` using the event name and `data.batch_id` as your deduplication key. Global webhook delivery already retries failed requests and non-`2xx` responses in Core 0.15.8. Apply the same deduplication to the new queued rollback event before it triggers any side effects. If your code matches the old message text, switch to the event name. See [Bulk transactions](/transactions/bulk-transactions#webhook-notifications) and [Global webhooks](/webhooks/global-webhooks#delivery-semantics).

## Monitor updates

From 0.15.9, `PUT /balance-monitors/{monitor_id}` changes only the fields you send. A partial body used to fail with `500`.

**What to do:** If your app sends `precision` without `value`, include `value` in the same request to change the scale. If your app does not send `precision` alone, no change is required. See [Update balance monitor](/reference/edit-balance-monitor).

## Negative split distributions

A negative `distribution` used to be accepted, and the `"left"` leg received the difference. From 0.15.9, negative `distribution` and `precise_distribution` values return `400 TXN_VALIDATION_ERROR`; no balance moves.

**What to do:** Send `0` or a positive value for each leg. See [Split transactions](/transactions/split-transactions#distribution).

## Balance history

Balance history could miss a backdated transaction or count a future-dated one twice. From 0.15.9, each transaction is counted once, at its `effective_date`.

Snapshots taken before the upgrade are skipped until new ones replace them. `from_source=true` results do not change.

**What to do:** Expect some past balances to change. If you store history results, read them again, and take a snapshot after you upgrade. See [Historical balances](/balances/historical-balances#how-it-works).
