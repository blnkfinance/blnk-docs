In a ledger, recording the payment is the start. Reports, investigations, and reviews all read that same history afterward.

Running those reads on the live database competes with the service that posts transactions, and the ledger slows down under work it still has to do.

The data lake is a separate copy of `transactions`, `balances`, `ledgers`, and `identity`, kept so those reads can easily work with billions of records without pressure on the live ledger instance. Insights and [Create new query](/reference/create-new-query) run SQL on the copy. The ledger stays the source of truth.

## How it works

Blnk reads posted records from the ledger on a schedule and writes them to daily Parquet files.

Each day of history is stored in its own files. Blnk does not edit a file after writing it. A record that arrives later is added in a new file, for the day that record was posted.

A query has a date range. DuckDB opens the files for those days and runs the SQL on them. Days outside that range are not part of the query.

<LakeFlow />

<Note>
You are not querying a replica of the ledger's Postgres database. The dialect is [DuckDB SQL](https://duckdb.org/docs/stable/sql/introduction.html), built for scans, aggregations, and joins over this copy. [Queries](/lake/queries) lists the statements the lake accepts.
</Note>

## What you use it for

Write the SQL yourself, or start from a [template](/lake/templates). The same copy serves a period report, a dashboard, and an AI client.

<Steps>
  <Step title="Break down posted volume">
    Total posted volume, then break it down by currency, day, or status, and see whether a period is up or down.

    Those scans run on the lake, including when the history runs into billions of records.
  </Step>
  <Step title="Write your own SQL">
    Send one read-only DuckDB `SELECT` or `WITH` from Insights or [Create new query](/reference/create-new-query).

    This statement finds a common monitoring case: a balance that received money and sent nearly the same amount straight back out. It joins that balance to its ledger and its identity.

    ```sql Pass-through balances expandable
    WITH applied AS (
      SELECT
        currency,
        source,
        destination,
        TRY_CAST(precise_amount AS DECIMAL(38, 8))
          / NULLIF(TRY_CAST(precision AS DECIMAL(38, 8)), 0) AS amount
      FROM transactions
      WHERE status = 'APPLIED'
    ),
    inflow AS (
      SELECT
        destination AS balance_id,
        currency,
        SUM(amount) AS inflow
      FROM applied
      GROUP BY 1, 2
    ),
    outflow AS (
      SELECT
        source AS balance_id,
        currency,
        SUM(amount) AS outflow
      FROM applied
      GROUP BY 1, 2
    ),
    balances_one AS (
      SELECT
        balance_id,
        ANY_VALUE(ledger_id) AS ledger_id,
        ANY_VALUE(identity_id) AS identity_id
      FROM balances
      GROUP BY balance_id
    ),
    ledgers_one AS (
      SELECT
        ledger_id,
        ANY_VALUE(name) AS ledger_name
      FROM ledgers
      GROUP BY ledger_id
    ),
    identity_one AS (
      SELECT
        identity_id,
        ANY_VALUE(identity_type) AS identity_type,
        ANY_VALUE(first_name) AS first_name,
        ANY_VALUE(last_name) AS last_name,
        ANY_VALUE(organization_name) AS organization_name,
        ANY_VALUE(email_address) AS email_address
      FROM identity
      GROUP BY identity_id
    )
    SELECT
      f.balance_id,
      f.currency,
      l.ledger_name,
      i.identity_type,
      i.organization_name,
      i.first_name,
      i.last_name,
      i.email_address,
      f.inflow,
      o.outflow,
      LEAST(f.inflow, o.outflow) AS passed_through
    FROM inflow f
    JOIN outflow o
      ON o.balance_id = f.balance_id
      AND o.currency = f.currency
    JOIN balances_one b ON b.balance_id = f.balance_id
    JOIN ledgers_one l ON l.ledger_id = b.ledger_id
    JOIN identity_one i ON i.identity_id = b.identity_id
    WHERE f.inflow > 0
      AND o.outflow > 0
      AND LEAST(f.inflow, o.outflow) / GREATEST(f.inflow, o.outflow) >= 0.8
    ORDER BY passed_through DESC
    LIMIT 100
    ```
  </Step>
  <Step title="Run business intelligence on billions of rows">
    Join `transactions`, `balances`, `ledgers`, and `identity`, group the rows, and use a window when a result needs the rows around it.

    That calculation can cover billions of records on the copy, and the figure it returns was never stored as its own record.

    <Warning>
    Running this calculation with [Search via DB](/search/db/filtering) makes the query time out. It also slows the ledger for the rest of the day's transactions.
    </Warning>
  </Step>
  <Step title="Run a report from a dashboard">
    Save the statement in [Queries](/lake/queries) and run it on a schedule, or call it from your own BI tool through [Create new query](/reference/create-new-query).

    That SQL is the report. It does not need a separate warehouse in front of the ledger.

    ![Insights SQL workbench with a saved query, date range, Run button, and results table](img/insights/insights-sql-workbench.png)
  </Step>
  <Step title="Let an AI client query the copy">
    The [MCP server](/ai/mcp) gives a client this copy as a store it can query. It can look for failed payments, unusual volume, a fraud pattern, or another question you describe.

    Those reads stay off the live ledger.
  </Step>
</Steps>

## When to use it

Use the lake for activity over a period. Use the ledger when you need what a wallet holds right now.

| Question | Where to get it |
| :-- | :-- |
| Money that moved over a period | [Queries](/lake/queries) or [Create new query](/reference/create-new-query) |
| Wallets, ledgers, and identities in that history | [Queries](/lake/queries) or [Create new query](/reference/create-new-query) |
| Amount in a wallet right now | [Get balance](/reference/get-balance) |
| Amount in a wallet at a past time | [Historical balances](/balances/historical-balances) |

[Schema](/lake/schema) lists the columns and how the four tables join.
