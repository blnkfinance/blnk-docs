<Version>Available in version 0.6.0 and later.</Version>

A split moves money in one request, with more than one balance on a single side. Send `sources` when several balances pay one destination. Send `destinations` when one balance pays several recipients.

<Warning>
A split is one side only. A payload that includes both `sources` and `destinations` is rejected with `400 TXN_VALIDATION_ERROR`.
</Warning>

## Multiple sources

Pooling contributions, topping up a wallet from multiple linked accounts, or settling an invoice from more than one internal pot are common use cases for multiple sources.

For example, Sarah should receive **USD 30,000** **into** her balance. Alice contributes 10%, Bob sends a fixed \$20,000, and Charlie’s contribution uses `"left"` so whatever remains after the first two legs comes from Charlie automatically.

Money movement would look like this:

![Multiple sources transaction flow](img/transactions/multiple-sources-flow.png)

<Map
  src="https://map.blnkfinance.xyz/GvPWMwzF3r"
  title="Multiple sources"
/>

| | Balance ID | Amount |
| :--- | :--- | :--- |
| Alice | bln_f2073f6b-905a-4e3e-b5a2-8d1b3dc2fb7f | 10% (USD 3,000) |
| Bob | bln_64c50fb5-32d5-4f78-9f4a-e8b01aaf025d | USD 20,000 |
| Charlie | bln_7d98dfe9-5c3e-4c9b-b96a-65f6d9f7b89b | Remaining amount (USD 7,000) |
| **Sarah (Recipient)** | bln_92e4b9b6-0b85-4ef4-87a2-682c31500d38 | **Total: USD 30,000** |

<Warning>
When sending from multiple sources, you can only send to one destination. A payload that includes both `sources[]` and `destinations[]` is rejected with `400 TXN_VALIDATION_ERROR`.
</Warning>

### Create the transaction

Call [Create transaction](/reference/create-transaction) with these fields.

To preview the split without writing it, set `dry_run` to `true`. See [Dry-run transactions](/transactions/dry-run).

<CodeGroup>
```bash cURL wrap expandable
curl -X POST http://localhost:5001/transactions \
  -H "Content-Type: application/json" \
  -H "X-Blnk-Key: <api-key>" \
  -d '{
    "precise_amount": 3000000,
    "precision": 100,
    "reference": "ref_001adcfgf",
    "currency": "USD",
    "sources": [
        {
            "identifier": "bln_f2073f6b-905a-4e3e-b5a2-8d1b3dc2fb7f",
            "distribution": "10%"
        },
```

| Field | Description | Required |
| :--- | :--- | :--- |
| `precise_amount` | Total amount to be received in its smallest unit. Send either `precise_amount` or `amount`, not both - see [Precision](/transactions/precision#using-both-precision-options-together). | Yes |
| `amount` | Total amount to be received as a float. Blnk multiplies by `precision` to store `precise_amount`. | Yes |
| `precision` | Precision for the transaction currency. See [Understanding precision](/transactions/precision) | No |
| `reference` | Unique transaction reference | Yes |
| `currency` | Asset class code. | Yes |
| `sources` | Array of source objects with `identifier` and `distribution` fields | Yes |
| `sources.identifier` | Balance ID of the source account | Yes |
| `sources.distribution` | Amount to send from this source (specific amount, percentage, or "left") | Yes |
| `destination` | Recipient's balance ID | Yes |
| `atomic` | When `true`, all source legs succeed or the entire split fails. Default: `false`. | No |
| `meta_data` | Custom transaction data | No |

<Warning>
    When sending from multiple sources, do not include the `source` field in your payload. Use the `sources` array to group the participating balances in your payload.
</Warning>

### API response structure

When you create a multiple sources transaction, Blnk records one coordinated request and creates separate ledger movements per source-all credited to the single **destination**.

Blnk returns a response containing:
- A **main transaction ID** for the overall split transaction. If `inflight: true`, it can be used to commit or void all transactions at once.
- A **sources array** with individual transaction IDs for each source.

## Multiple destinations

**One sender, many recipients** is pretty common: a payroll run, a marketplace split, or a refund that returns funds to several customer wallets at once.

For example, Sarah is sending **USD 30,000** **out** of her balance. She routes 20% to Alice, a fixed \$10,000 to Bob, and assigns `"left"` to Charlie so whatever remains after the first two legs goes to Charlie automatically.

Money movement would look like this:

![Multiple destinations transaction flow](img/transactions/multiple-destinations-flow.png)

<Map
  src="https://map.blnkfinance.xyz/2MmTXXT8tj"
  title="Multiple destinations"
/>

| | Balance ID | Amount |
| :--- | :--- | :--- |
| Alice | bln_f2073f6b-905a-4e3e-b5a2-8d1b3dc2fb7f | 20% (USD 6,000) |
| Bob | bln_64c50fb5-32d5-4f78-9f4a-e8b01aaf025d | USD 10,000 |
| Charlie | bln_7d98dfe9-5c3e-4c9b-b96a-65f6d9f7b89b | Remaining amount (USD 14,000) |
| **Sarah (Sender)** | bln_92e4b9b6-0b85-4ef4-87a2-682c31500d38 | **Total: USD 30,000** |

From a product perspective, that usually maps to one user-facing action (“Send \$30k”) while your ledger still exposes each recipient line for reporting, disputes, or partial reversals.

<Warning>
When sending to multiple destinations, you can only send from one source. A payload that includes both `sources[]` and `destinations[]` is rejected with `400 TXN_VALIDATION_ERROR`.
</Warning>

This will return all individual transactions that were created as part of the multiple destinations transaction, allowing you to track and manage the complete set of related transactions.


## Distribution

You can specify distribution amounts in three ways. The same rules apply to `sources` and to `destinations`.

| Type | Description | Example |
| :--- | :--- | :--- |
| **Specific amount** | Fixed amount. Use `precise_distribution` when the transaction uses `precise_amount`. | `"precise_distribution": "2000000"` |
| **Percentage** | Percentage of the total amount | `"distribution": "10%"` |
| **Remaining** | Whatever is left after the other legs | `"distribution": "left"` |

<Warning>
You can only use `"left"` once per transaction, and all distributions must sum to the total amount.
</Warning>

### Using `precise_distribution` with `precise_amount`

When a transaction uses `precise_amount`, use `precise_distribution` instead of `distribution` only for legs that specify an exact value. Percentages (`"10%"`) and the remainder (`"left"`) still use `distribution`.

```json Example with precise_amount wrap
{
  "precise_amount": 189207535698279000,
  "sources": [
    {
      "identifier": "bln_f2073f6b-905a-4e3e-b5a2-8d1b3dc2fb7f",
      "precise_distribution": "37841507139655800"
    },
    {
      "identifier": "bln_64c50fb5-32d5-4f78-9f4a-e8b01aaf025d",
      "distribution": "20%"
    }
  ]
}
```

<Tip>
For how `precise_amount` and `precision` work, see [Precision](/transactions/precision).
</Tip>

## Atomic processing

By default, Blnk processes a split with `atomic: false`. Each leg is evaluated on its own. Legs that pass are marked `APPLIED`, and legs that fail are marked `REJECTED`. That can leave a partial split.

Set `atomic: true` for all-or-nothing processing. Every leg must succeed. If any leg fails, Blnk rolls back legs that already applied or went inflight. A failed source leg reverses the debits. A failed destination leg reverses the credits. The split is cancelled and no partial state remains.

<Tip>
Use `atomic: true` when a partial result is not acceptable, such as settling an invoice where every contributor must cover its share, or paying out a split where every recipient must succeed.
</Tip>

## Retrieving the child transactions

Blnk records one coordinated request and a separate ledger movement for each leg. Retrieve those movements by searching for the main transaction ID in `meta_data.QUEUED_PARENT_TRANSACTION`.

<CodeGroup>
```bash cURL wrap
curl -X POST "http://localhost:5001/search/transactions" \
  -H "X-blnk-key: <api-key>" \
  -H "Content-Type: application/json" \
  -d '{
    "q": "<queued_parent_transaction_id>",
    "query_by": "meta_data.QUEUED_PARENT_TRANSACTION"
  }'
```
</CodeGroup>

The search returns every transaction created as part of the split.

## Transaction references

Blnk generates a unique reference for each leg by appending a counter to your reference, starting at `1`. From version 0.15.4 the suffix follows the order of the array you sent, `sources` or `destinations`, and stays stable across retries.

If your reference is `ref_001adcfgf`, the legs are `ref_001adcfgf_1`, `ref_001adcfgf_2`, and `ref_001adcfgf_3`.
