<Version>Available in version 0.6.0 and later.</Version>

A split moves money in one request, with more than one balance on a single side. 

Send `sources` when several balances pay one destination. Send `destinations` when one balance pays several recipients.

<Warning>
A split is one side only. A payload that includes both `sources` and `destinations` is rejected with `400 TXN_VALIDATION_ERROR`.
</Warning>

## Record split

Sarah's balance is `bln_92e4b9b6-0b85-4ef4-87a2-682c31500d38`. Alice, Bob, and Charlie use the same balances in both scenarios. Alice's leg is a percentage, Bob's is a fixed amount, and Charlie's is `"left"`.

**Several sources.** They pay Sarah **USD 30,000**. Alice sends 10%, Bob sends \$20,000, and Charlie sends the rest.

### Using the API

Call [Create transaction](/reference/create-transaction). Send `sources` instead of `source`, or `destinations` instead of `destination`. To preview the split without writing it, set `dry_run` to `true`. See [Dry-run transactions](/transactions/dry-run).

Blnk returns one id for the split, and an id for each leg on the array you sent. With `inflight: true`, that split id commits or voids every leg. See [Record split inflight transaction](/transactions/inflight/create-inflight#record-split-inflight-transaction).

## How it works

### Distribution

You can specify distribution amounts in three ways. The same rules apply to `sources` and to `destinations`.

| Type | Description | Example |
| :--- | :--- | :--- |
| **Specific amount** | Fixed amount. Use `precise_distribution` when the transaction uses `precise_amount`. | `"precise_distribution": "2000000"` |
| **Percentage** | Percentage of the total amount | `"distribution": "10%"` |
| **Remaining** | Whatever is left after the other legs | `"distribution": "left"` |

<Warning>
You can only use `"left"` once per transaction, and all distributions must sum to the total amount.
</Warning>

When a transaction uses `precise_amount`, use `precise_distribution` instead of `distribution` only for legs that specify an exact value. Percentages (`"10%"`) and the remainder (`"left"`) still use `distribution`.

```json Example with precise_amount wrap
{
  "precise_amount": 189207535698279000,
  "sources": [
    {
      "identifier": "bln_f2073f6b-905a-4e3e-b5a2-8d1b3dc2fb7f",
      "precise_distribution": "37841507139655800"
    },
    {
      "identifier": "bln_64c50fb5-32d5-4f78-9f4a-e8b01aaf025d",
      "distribution": "20%"
    }
  ]
}
```

<Tip>
For how `precise_amount` and `precision` work, see [Precision](/transactions/precision).
</Tip>

### Transaction references

Blnk generates a unique reference for each leg by appending a counter to your reference, starting at `1`. 

From version `0.15.4` the suffix follows the order of the array you sent, `sources` or `destinations`, and stays stable across retries.

If your reference is `ref_001adcfgf`, the legs are `ref_001adcfgf_1`, `ref_001adcfgf_2`, and `ref_001adcfgf_3`.

### Retrieving child transactions

Blnk records one coordinated request and a separate ledger movement for each leg. Filter on `meta_data.QUEUED_PARENT_TRANSACTION` to retrieve those movements.

<CodeGroup>
```bash cURL wrap

  -H "X-blnk-key: <api-key>" \
  -H "Content-Type: application/json" \

      {
        "field": "meta_data.QUEUED_PARENT_TRANSACTION",
```

### Atomic processing

By default, Blnk processes a split with `atomic: false`. Each leg is evaluated on its own. Legs that pass are marked `APPLIED`, and legs that fail are marked `REJECTED`. That can leave a partial split.

Set `atomic: true` for all-or-nothing processing. Every leg must succeed. If one leg fails, Blnk refunds the legs that already processed. Each refund cancels that movement, so the split does not leave a partial result.

<Tip>
Use `atomic: true` when a partial result is not acceptable, such as settling an invoice where every contributor must cover its share, or paying out a split where every recipient must succeed.
</Tip>
