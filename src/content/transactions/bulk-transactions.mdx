<Version>Available in version 0.9.0 and later.</Version>

The Bulk Transaction API enables you to process multiple transactions within a single request. Use `atomic: true` to roll back work after a processing failure. On the default queued path, a failure while adding items to the queue can leave earlier items active, even with `atomic: true`. See [Atomic processing](#atomic-processing).

Additionally, the API supports asynchronous processing to efficiently manage large batches of transactions.

To preview a batch without writing anything, set `dry_run` to `true`. See [Dry-run transactions](/transactions/dry-run).

## Creating bulk transactions

<Steps>
<Step title="Configure and submit the batch">

Call the [Bulk Transactions API](/reference/bulk-transactions). 

<Version>From Blnk Core **0.10.5**, bulk create defaults to `skip_queue: false` and enqueues each item. Before 0.10.5, every item was processed synchronously in the request.</Version>

</CodeGroup>

| Field | Description |
| :-- | :-- |
| `atomic` | When `true`, Blnk rolls back work after a processing failure. Items already queued can still process if submission fails while queueing. When `false`, Blnk processes items independently. See [Atomic processing](#atomic-processing). |
| `inflight` | When `true`, transactions are created in `INFLIGHT` status and require a separate commit. When `false`, transactions are processed immediately. |
| `run_async` | When `true`, processing happens in the background and results are delivered via webhook. When `false` or not provided, processing happens synchronously and results are returned in the response. |
| `skip_queue` | Defaults to `false`. When `true`, transactions bypass the queue and are processed inline in the request. Affects duplicate-reference handling - see [Duplicate references](#duplicate-references). |
| `transactions` | Array of transaction objects. Max of 10,000 transactions per request. |

<Step title="Confirm the response">

Blnk returns a `batch_id` that identifies the batch. When `skip_queue: false`, Blnk stores `batch_id` as the queued parent transaction. 

Save it. You can use the same ID to retrieve, commit, refund, or void every transaction in the batch without tracking individual child IDs first. See [Retrieving transactions in a batch](#retrieving-transactions-in-a-batch).

## Atomic processing

With `atomic: true`, the outcome depends on where the failure occurs.

| Failure phase | What Blnk does |
| :--- | :--- |
| Adding items to the queue (`skip_queue: false`) | Stops adding items at the failure. Items already queued may still process and move balances. |
| Processing a queued item (`skip_queue: false`) | On rejection, refunds applied items or voids inflight items and sends `bulk_transaction.failed`. As Blnk reaches the items still waiting in the queue, it records them as `REJECTED`. |
| Processing inline (`skip_queue: true`) | On failure, refunds applied items or voids inflight items from the batch and stops processing later items. |

## Retrieving transactions in a batch

When you submit a bulk transaction request, Blnk assigns each transaction in the batch its own unique transaction ID and links it to your `batch_id`:

- **`skip_queue: false` (default):** child transactions record `batch_id` in `meta_data.QUEUED_PARENT_TRANSACTION`.
- **`skip_queue: true`:** child transactions set `parent_transaction` to `batch_id`.

## Handling inflight bulk transactions

Set `inflight: true` on the bulk request. Blnk ignores an `inflight` flag on child objects and holds every transaction in the batch. See [Record bulk inflight transaction](/transactions/inflight/create-inflight#record-bulk-inflight-transaction).

Commit or void the batch with `batch_id`. See [Commit a split or a bulk batch](/transactions/inflight/commit-inflight#commit-a-split-or-a-bulk-batch) and [Void a split or a bulk batch](/transactions/inflight/void-inflight#void-a-split-or-a-bulk-batch).

Holds created one by one use [Commit multiple inflights](/transactions/inflight/commit-inflight#commit-multiple-inflights) and [Void many transactions](/transactions/inflight/void-inflight#void-many-transactions).

## Webhook notifications

When using `run_async: true`, the API sends webhook notifications upon completion or failure.

When a worker rejects an item in a queued atomic batch, Blnk sends `bulk_transaction.failed` for either value of `run_async`. Blnk sends the event after it refunds any applied transactions or voids any inflight transactions. The `error` field says how many transactions were rolled back. Items still waiting in the queue can receive their `REJECTED` records after the webhook. Check the [batch records](#retrieving-transactions-in-a-batch) for each item’s outcome.

Blnk emits one failure event for a queued atomic batch rejected by a worker. Delivery can be retried. Make your handler idempotent using `event` and `data.batch_id` together. See [Global webhooks](/webhooks/global-webhooks#delivery-semantics).

The webhooks follow this structure:

```json Response
{
  "event": "bulk_transaction.applied",
  "data": {
    "batch_id": "bulk_c62f200b-905f-4983-a349-cadd279234aa",
    "status": "applied",
    "transaction_count": 4,       
    "error": "error message",     
    "timestamp": "2025-03-02T15:30:45+01:00"
  }
}
```

| **Field** | **Type** | **Description** |
| :-- | :-- | :-- |
| `event` | String | Name of event. Can be `bulk_transaction.applied`, `bulk_transaction.inflight`, or `bulk_transaction.failed`. |
| `batch_id` | String | Specifies the id of the batch transaction. |
| `status` | String | Status of the batch transaction. Can be `applied`, `inflight`, or `failed`. |
| `transaction_count` | String | Number of transactions in the batch. Only included for successful cases. |
| `error` | String | Error message. Only included for failure cases. |
| `timestamp` | String | Specifies the date & time when the batch transaction was completed. |

## Error handling

<Version>Structured errors are available from Blnk Core 0.15.0 and later.</Version>

Bulk endpoints return structured `error_detail` objects for validation failures. For duplicate references and batch rollbacks, behaviour depends on `skip_queue`. See [API error codes](/operating/error-codes) for the full catalogue.

### Request validation errors

Blnk returns `400` when the request body fails validation before processing starts.

| Code | When it happens |
| :-- | :-- |
| `TXN_BULK_EMPTY` | `transactions` array is empty |
| `TXN_BULK_LIMIT_EXCEEDED` | More than 10,000 items in `transactions` |
| `TXN_VALIDATION_ERROR` | A transaction object is null or invalid |

For `TXN_VALIDATION_ERROR`, `error_detail.details.index` identifies the zero-based position in `transactions[]`:

```json 400 Bad Request wrap
{
  "error_detail": {
    "code": "TXN_VALIDATION_ERROR",
    "message": "transactions[1]: currency: cannot be blank; destination: either destination or destinations is required, not both.",
    "details": {
      "index": 1
    }
  },
  "errors": "transactions[1]: currency: cannot be blank; destination: either destination or destinations is required, not both."
}
```

### Duplicate references

Duplicate-reference handling depends on whether items go through the queue.

<Tabs>
<Tab title="skip_queue: false">

Blnk saves items as it queues them. When it encounters a used reference, it stops at that item. With `run_async: false`, the request returns `409 TXN_DUPLICATE_REFERENCE`. With `run_async: true`, Blnk reports the failure through `bulk_transaction.failed` after accepting the request.

<Warning>
Items queued before the duplicate can still move balances, even with `atomic: true`. Reconcile the batch before submitting any of its items again.
</Warning>

### Reconcile a queued batch after a duplicate reference

Derive each reference from a stable business operation ID and a stable item ID, such as `payout-8472-recipient-03`. Keep the same reference for the same intended movement across attempts, and use distinct references for distinct movements. A lookup before submission can detect an existing reference, but concurrent submissions can still race.

1. Save the `batch_id` from the `409` response or the asynchronous failure webhook. Keep the original ordered list of references. If the error identifies a position such as `transactions[1]`, use that zero-based index to identify the duplicate and the items before it.
2. [Retrieve transactions in the failed batch](#retrieving-transactions-in-a-batch) by filtering on `meta_data.QUEUED_PARENT_TRANSACTION`. Use [Get transaction by reference](/reference/get-transaction-by-reference) to check the duplicate and each original reference, including items after the duplicate. Compare the batch ID, source, destination, currency, and amount with your records to distinguish this attempt from another submission.
3. Track queued items until you can account for their outcome. Check for applied movements, inflight holds, rejections, and any refunds or voids. If the original record is still `QUEUED`, check its [child transactions](/transactions/parent-transactions). If you still cannot account for the item, leave it pending in your application and recheck.
4. Submit only movements that you confirm are still needed and have no accepted transaction. Keep their original references. If an existing transaction needs to be reversed or replaced, handle that as a separate operation after you verify its outcome. Never resend the entire batch or generate new references to bypass the conflict.

## Important notes

1. Blnk submits items in request order. Use each queued item’s status to verify when it finishes.
2. Each transaction’s `reference` must be unique. Use stable references so you can reconcile duplicate submissions. See [Duplicate references](#duplicate-references).
3. When `run_async` is `true`, processing happens in the background and you'll receive an immediate response with a batch ID.
4. For large transaction batches, using `run_async: true` is recommended to avoid timeout issues.
5. Webhook notifications for async processing contain the same detailed error information as synchronous responses, including rollback status.
6. On the default queued path, `status: "applied"` means the bulk request was accepted. Filter on `parent_transaction` or `meta_data.QUEUED_PARENT_TRANSACTION` to verify final child statuses.
