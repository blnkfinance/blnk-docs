Payments, transfers, settlements, and treasury moves are all transactions. Create the [balances](/balances/introduction) inside a [ledger](/ledgers/introduction) first.

## Transaction properties

1. **Double entry:** Every transaction has a source and a destination. See [Double entry](/guides/double-entry).

2. **Immutability:** Once recorded, a transaction cannot be modified or deleted. See [Transaction hashing](/transactions/hash).

3. **Idempotency:** The same request produces the same result each time you send it.

    <Warning>
      Blnk requires a unique `reference` for every transaction. That reference stops a retry from recording the transaction twice.
    </Warning>

## Queue and skip queue

When you record a transaction, Blnk queues it by default and processes it asynchronously. The call returns first with a `QUEUED` status, and a worker picks it up and processes it eventually. 

The initial `QUEUED` response signifies that the request was accepted; final results can be verified via events or polling.

Alternatively, you can set `skip_queue` to `true` to apply transactions synchronously. Blnk tries to process it immediately, and return the final result in the response.

## Managing insufficient funds

<Version>Available in version 0.11.0 and later.</Version>

Blnk always checks the source before it records a transaction. Available balance is calculated as `balance - inflight_debit_balance`.

We subtract inflight debit because it is the amount reserved from the balance. If the amount is higher than the available balance, the result depends on the queue.

<Tabs>
<Tab title="Default queue">

The API first returns a `QUEUED` transaction. The worker then records a separate `REJECTED` transaction.

That record points back with `parent_transaction` and stores the reason in `meta_data.blnk_rejection_reason`. Blnk sends a `transaction.rejected` webhook for it.

With the default queue, Blnk records `REJECTED` on the first failure. If [insufficient-fund retries](/advanced/configuration/queue) are enabled, it records `REJECTED` only after those retries are exhausted.

</Tab>
<Tab title="Skip queue">

When `skip_queue: true`, Blnk processes the request immediately and returns `400 TXN_INSUFFICIENT_FUNDS`.

The rejected attempt is not recorded, so the `reference` is not used. You can retry the same `reference` after the source has enough funds.

</Tab>
</Tabs>

<Note>
Set `allow_overdraft` to `true` to let the transaction proceed when the source does not cover it. [Learn more](/transactions/overdrafts).
</Note>

## Discarded transactions

Some requests are not recorded in the ledger.

1. **Duplicate reference:** The `reference` matches one already in the ledger. Use a unique value, such as a timestamp, a UUID like `ref_e55c4f33-bff7-4c30-9b9f-5d2d10a29b7a`, or an `order_id`.

2. **Zero amount:** The amount is 0. Blnk does not record a zero amount.

3. **Insufficient funds with `skip_queue: true`:** The rejected attempt is not recorded. See [Managing insufficient funds](#managing-insufficient-funds).

<Tip>
Match the request to the expected API shape. Pass `allow_overdraft`, not `apply_overdraft`.
</Tip>
